# Porting the examples to pixi

An honest attempt to express each of denver's seven bundled examples as a
[pixi](https://pixi.sh) project, to find out where the two tools actually
disagree.

**These ports are unverified.** pixi is not installed in the environment this
branch was produced in, so nothing here has been solved, locked or run. Package
names and version availability on conda-forge are marked UNVERIFIED inline
wherever they were assumed rather than checked. Treat this as a design
comparison, not as working configuration.

Ports are additive: each `pixi.toml` sits next to the `denver.yml` it was
derived from, so the two can be read side by side. No example was modified.

## Result per example

| Example | Ported | Fidelity |
|---|---|---|
| `simple-env` | [`simple-env/pixi.toml`](simple-env/pixi.toml) | Partial — no CLI-arg declaration, no "before" hook |
| `zephyr-uv` | [`zephyr-uv/pixi.toml`](zephyr-uv/pixi.toml) | **Full, and arguably better** — pixi adds a lockfile |
| `raspberry-pico` | [`raspberry-pico/pixi.toml`](raspberry-pico/pixi.toml) | Partial — pico-sdk has no conda-forge package |
| `zephyr-docker` | *not ported* | No equivalent — pixi has no container-wrapper concept |
| `howto-env` | [`howto-env/pixi.toml`](howto-env/pixi.toml) | 4 of 5 stages; the docker stage has no counterpart |
| `zephyr-devshell` (base) | *folded into 4.3.1* | No cross-folder inheritance |
| `zephyr-devshell-4.3.1` | [`zephyr-devshell-4.3.1/pixi.toml`](zephyr-devshell-4.3.1/pixi.toml) | Weak — west's post-clone resolution is inexpressible |

## What pixi does better

- **Lockfiles.** `pixi.lock` pins the full transitive solve for every declared
  platform. denver fingerprints `requirements.txt` and re-runs `uv pip install`;
  that detects change, but it does not pin a resolution. `zephyr-devshell-4.3.1`
  has a hand-rolled version of this (`freeze-to:` writing
  `requirements.final.txt` back into the tree, regenerated by re-running
  denver and committing the diff) — pixi gets the same property for free and
  more rigorously.
- **Cross-platform.** `platforms = [...]` solves for macOS and Windows from the
  same manifest. denver is Linux-only in practice (`Operating System :: POSIX
  :: Linux` in `pyproject.toml`).
- **One tool instead of three.** `zephyr-uv` and most of `howto-env` need uv +
  conan + a container in denver, and only pixi in pixi.
- **Python and native deps in one resolver.** denver's `uv` → `conan` ordering
  exists because conan is itself a pip package that must be installed before
  the stage named after it can run. pixi has no such bootstrap ordering problem.

## What did not port, and why

1. **The container wrapper.** `zephyr-docker` is denver's `docker` stage on its
   own, and it has no pixi counterpart at all. denver's model — a wrapper stage
   relocates every later stage into a container, and `--skip docker` runs the
   identical stack on the host — is a different answer to "same environment
   everywhere" than "pin conda-forge packages." pixi's answer is genuinely good
   and covers most cases; it does not cover *this glibc* or *this apt package*.

2. **Cross-folder inheritance.** denver's `import: [../zephyr-devshell]` pulls
   in another directory's whole env and overrides three keys. pixi composes via
   `[feature]`/`[environments]` within one manifest. The base/derived split that
   `zephyr-devshell` + `zephyr-devshell-4.3.1` exist to demonstrate had to be
   flattened into a single file, which loses the property being demonstrated.

3. **Dependencies that aren't knowable up front.** `uv-zephyr` installs whatever
   `west packages pip` reports *after* `west update` has cloned the workspace.
   A lockfile-first tool structurally cannot express this. This is the single
   hardest incompatibility in the set.

4. **Packages nobody has repackaged.** `pico-sdk` is not on conda-forge, and
   denver's recipe for it also builds `picotool` from source. denver fetches
   upstream release artifacts against committed recipes with pinned checksums,
   so it never depends on a third party having packaged the exact version you
   need. Whether that is an advantage or just unpaid packaging work depends
   entirely on whether the thing you need is already in conda-forge.

5. **Ordered build pipelines.** denver runs stages in order on entry, with
   per-stage fingerprinting and `--fast`/`--force`. pixi has activation and
   tasks, but no ordered multi-step setup pipeline where step N's exports feed
   step N+1. Everything in `simple-env` is about that mechanism, which is why it
   ports so poorly despite being the smallest example.

6. **Environment-specific CLI flags.** denver's `args:` declares real argparse
   flags that `denver <env> --help` lists. No pixi equivalent.

## Verdict

pixi wins outright for `zephyr-uv` and would win for the majority of ordinary
projects — anything whose native dependencies are already in conda-forge should
probably use pixi rather than denver. It does not reach `zephyr-docker`,
`zephyr-devshell-4.3.1`, or the pico-sdk half of `raspberry-pico`, and the
reasons are structural rather than missing features.
