# examples/zephyr-devshell-4.3.1

**A complete [Zephyr RTOS](https://zephyrproject.org) 4.3.1 development
environment — the largest example in the tree, and the one to actually run.**

```console
$ denver examples/zephyr-devshell-4.3.1
... denver builds/enters each layer ...
dev@container ~/workspace> west build -b nrf52840dk/nrf52840 samples/hello_world
dev@container ~/workspace> exit      # back to your normal shell
```

You did not install a compiler, create a virtualenv, clone twenty
repositories or write a bootstrap script. Nothing was installed on your host.

## What it does

Five stages, in order:

| # | Stage | What happens |
|---|-------|--------------|
| 1 | `docker` | Builds the image and drops you **inside a container** — same Linux, same system libraries, whether your laptop runs Ubuntu, Fedora or WSL |
| 2 | `conan` | Fetches **native, non-Python tools**: the Zephyr SDK cross-compilers, `cmake`, `ninja`, `ccache`, `clang`, the J-Link tools. Prebuilt binaries, so nothing compiles locally |
| 3 | `pip` | Creates a **virtualenv** with the pinned Python packages — above all `west`, Zephyr's repo-management tool |
| 4 | `zephyr` | `west update`: **clones the many repositories** of a Zephyr workspace at the revisions pinned for 4.3.1, applies this env's patches, fetches binary blobs |
| 5 | `pip-zephyr` | The modules from step 4 declare Python dependencies of their own (`west packages pip`). Installs **those**, into the venv from step 3 — it has to run after step 4, because until then nobody knew what they were |

Then denver hands control to `fish` with all five layers active.

## Why it exists

**Because this is the case that justifies the tool.** Setting up a Zephyr
workspace by hand is a genuinely hard, multi-hour, easy-to-get-subtly-wrong
job, and the result is nearly impossible to reproduce a year later. It is the
proof that the model scales past toy environments.

**Because it is deliberately the extreme, not the norm.** If this is your
first denver env, it will look like a lot. Almost none of it is denver: it is
Zephyr's own complexity, made explicit. Start at
[`../simple-env`](../simple-env) (three stages, one script) or
[`../zephyr-uv`](../zephyr-uv) (one stage) instead — the CLI and the model are
identical at both sizes.

## Why is `denver.yml` so short?

Under 60 lines, half of them comments, and **no `stages:` list and no docker
config at all** — because of `import:`:

```yaml
import:
- ../zephyr-devshell     # inherit that env's entire setup as a base
```

```
zephyr-docker/           "how to build & enter the container"
      ▲ imported by
zephyr-devshell/         the 5-stage pipeline, shared recipes, common env
      ▲ imported by
zephyr-devshell-4.3.1/   ONLY the 4.3.1-specific bits:
                         pinned requirements, conanfile, blob list
```

A Zephyr 4.4.0 env would be a new folder importing that same base and
changing only the pins. **This file is what "version-specific" means in
practice** — everything in it is a number, a pin or a patch.

## Purpose as an example

This is where to look for the patterns that only appear at scale.

**1. The lockfile pattern (`freeze-to:` → `requirements:`).** `pip-zephyr`
writes its fully-resolved `uv pip freeze` output to
`requirements.final.txt`; the `pip` stage then *reads that same file back in*
as one of its `requirements:`. So a fresh clone gets the exact resolved
versions without having to run `west packages pip` first — a lockfile
generated by the pipeline rather than maintained by hand.

Regenerate it by running denver once and committing the diff. **On a merge
conflict in that file, don't hand-resolve it**: take either side, re-run
denver on the merged branch, and commit the regenerated result.

**2. Nothing is inherited by proximity.** Three separate keys here exist
purely to say out loud what another tool would have guessed from the
directory layout — `skip-if:`, `venv-patcher: patches:`, and `pip-zephyr`'s
`overrides:`. That last one is the sharp edge: `pip-zephyr` shares the `pip`
stage's *venv*, but it does **not** inherit the `pip` stage's *config*. It
repeats `overrides:`, `skip-if:` and `venv-patcher:` itself, because a stage's
section is its own.

**3. Claiming the base's recipes.** The shared env ships recipes but declares
no `conanfiles:` unit for them (it has no conanfile). This env's unit lists
both directories explicitly, base first, and writes the merged catalog:

```yaml
conanfiles:
- path: conan/conanfile.py
  recipe-dirs:
  - ../zephyr-devshell/conan/recipes   # the shared ones
  - conan/recipes                      # its own
  catalog: conan/catalog.yml           # pins, reviewable in a diff
```

**4. Patching things you don't own.** Two different mechanisms, for two
different targets — and only the first is a denver feature:

- **`venv-patcher:`** is denver's: it patches installed *Python packages*,
  here three patches against `west` itself.
- **`zephyr/patches.yml`** is not a `denver.yml` key at all. It is west's own
  convention: `zephyr/module.yml` declares this env as a Zephyr module, which
  is what makes `west patches` find the file and apply it to the *workspace
  repositories* after `west update`. denver's only involvement is
  `patch-committer`, which defaults to a fixed identity and date so applying
  the same patch twice can't produce a different commit.

  The file is worth reading as a format regardless: each entry carries a
  `sha256sum`, whether it is `upstreamable`, the `merge-pr` URL and its
  `merge-status`. A carried patch is tracked as a debt with a link to where
  it goes away, not as an anonymous diff.

**5. Caching as a Conan package.** `conan/recipes/python-cache/` and
`west-blobs-cache/` package a wheel cache and a blob cache as ordinary Conan
recipes, so `conan` (stage 2) can supply them to `pip` (stage 3) via
`UV_FIND_LINKS` — which is the real reason `conan` runs before `pip` here,
and lets the pip install work offline.

**6. `skip-if:`.** `pip/skip-if.sh` is four lines: if `west` and `conan` are
both already on `PATH`, exit 0 and the install is skipped. This is the
"fast on repeat runs" behaviour made explicit and overridable — `--force`
ignores it.

## Files

| Path | What it is |
|---|---|
| `denver.yml` | The pins, and nothing else |
| `conan/conanfile.py` / `catalog.yml` | The tool set for 4.3.1, pinned by revision |
| `conan/recipes/python-cache/denver/` | Wheel cache; `requirements.final.txt` is the generated lockfile |
| `conan/recipes/west-blobs-cache/denver/` | Pre-cached west blobs (`blobs.txt`) |
| `pip/skip-if.sh` | The "already installed?" check |
| `pip/venv-patcher/west/` | Three patches applied to the installed `west` |
| `zephyr/patches.yml` + `patches/` | Patches `west patches` applies to workspace repos, with upstream status |
| `zephyr/module.yml` | Declares this env as a Zephyr module — what makes the two files above discoverable |
